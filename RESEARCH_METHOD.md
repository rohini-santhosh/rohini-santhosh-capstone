# How Narra research reports get made

Narra's deployed site never calls an AI API and needs no key or login — it's
a static library of research reports plus a small local queue for topic
requests. New reports are generated by asking Claude (in a Claude Code
session on this repo) to research a topic; Claude does the actual work using
its own web search, then publishes the result into `public/research/`.

This doc is the checklist/spec Claude should follow each time, so every
report — regardless of which session generated it — has the same shape and
rigor.

## Process

1. Pick a topic (from a user request, or from `server/data/requests.json` —
   see below).
2. **Gather real sources** — actually search the web for 4-6 diverse, real,
   publicly accessible sources (forums, reviews, blog essays, support
   threads, case studies). Never invent a URL or quote.
3. **Extract observations** — 15-30 atomic observations, each with an exact
   quote, the real source URL, and a sentiment (`praise` / `complaint` /
   `workaround` / `feature_request`). Pick 8-12 of the strongest as
   `primary_research_quotes`.
4. **Insights** — cluster observations into 3-5 insights. Each gets a
   frequency (observation count), a severity (1-5), and `rank = frequency ×
   severity`. Rank insights by impact.
5. **Pain points & needs** — pair each major pain point with the underlying
   user need and evidence.
6. **Behavior patterns** — 2-4 recurring loops as `[Trigger] -> [Action] ->
   [Context] -> [Outcome]`, each backed by 2+ observations.
7. **Behavior personas** — 2-4 archetypes built from the observations (never
   invented stereotypes): goals, patterns, pain points, constraints,
   evidence quotes.
8. **Contradictions** — genuine tensions in the data (what users say vs. do,
   two personas wanting opposite things, common wisdom contradicted by
   evidence). Don't smooth these over — they're often the most useful part.
9. **Journey map** — walk one representative persona through the lifecycle
   (e.g. Discover → Onboard → Early use → Hits friction → Consequence →
   Decision → Outcome). Each stage: actions, thoughts/emotions, pain points,
   an opportunity.
10. **Flows** — for the 2-3 biggest friction points, describe the current
    step-by-step flow and a proposed improved flow.
11. **Summary** — a few sentences tying the whole report together.
12. **Product opportunity & direction** — 3-5 opportunities, each with a
    concrete design direction, a rationale, and supporting evidence.
13. **Self-check** before publishing — grade the draft against the 10 points
    below; strengthen anything weak rather than shipping it thin.

## 10-point quality bar

1. Traceability — every observation/quote from a real URL, nothing invented
2. Diverse sources — 4-6+ distinct sources, varied types where possible
3. Insight evidence — 3+ observations per insight, ranking math shown
4. Behavior patterns — 2+ observations per pattern
5. Personas grounded — built from observations, not stereotypes
6. Pain points specific — concrete, each tied to a clear user need
7. Contradictions genuine — real tensions, not manufactured
8. Journey map complete — Discovery through Outcome, opportunity per stage
9. Flows actionable — current vs. proposed, concrete enough to prototype
10. Product opportunities actionable — each ties to evidence with a clear rationale

## Output shape

Write the result as a single JSON file matching this shape exactly (see
`public/research/task-management-app-abandonment.json` for a full worked
example):

```json
{
  "topic": "string",
  "scope": "string",
  "gather_data": { "methodology": "string", "sources": [{ "url": "", "title": "", "type": "" }] },
  "primary_research_quotes": [{ "quote": "", "source_url": "", "sentiment": "" }],
  "insights": [{ "insight": "", "frequency": 0, "severity": 0, "rank": 0, "evidence_quotes": [] }],
  "observations": [{ "id": "", "observation": "", "source_url": "", "quote": "", "sentiment": "" }],
  "pain_points_and_needs": [{ "pain_point": "", "need": "", "evidence_quotes": [] }],
  "behavior_patterns": [{ "trigger": "", "action": "", "context": "", "outcome": "" }],
  "behavior_personas": [{ "name": "", "archetype": "", "goals": [], "patterns": [], "pain_points": [], "constraints": [], "evidence_quotes": [] }],
  "contradictions": [{ "contradiction": "", "explanation": "", "evidence_quotes": [] }],
  "journey_map": [{ "stage": "", "user_actions": "", "thoughts_emotions": "", "pain_points": "", "opportunities": "" }],
  "flows": [{ "name": "", "steps": [] }],
  "summary": "string",
  "product_opportunity_and_direction": [{ "opportunity": "", "direction": "", "rationale": "", "evidence_quotes": [] }],
  "validation": { "revisions": 0, "rubric_note": "string" }
}
```

## Publishing a new report

1. Save the JSON to `public/research/<slug>.json` (kebab-case slug).
2. Add an entry to `public/research/index.json`: `{ "slug", "topic", "scope", "createdAt" }`.
3. No server restart needed — both are served as static files.

## Picking up requested topics

Visitors can queue a topic via the "Suggest a topic" box on the site, which
POSTs to `/api/requests` and appends to `server/data/requests.json` (gitignored
— it's runtime data, not source). Check that file for pending requests, and
once a topic is published, remove its entry (or mark it done) — there's no
UI for this yet, it's a plain JSON array to edit by hand.
